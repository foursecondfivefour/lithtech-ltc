# ANALYSIS-4 — LTC (`tools/LTC`): рекогносцировка перед портированием

Дата: 2026-11-06. Источник: публичное зеркало `jsj2008/lithtech` (ветка `master`).
Предыдущий проект (`Model_Packer`, M1–M5) — https://github.com/foursecondfivefour/lithtech-model-packer.

---

## 1. Итог в четырёх строках

`LTC` — это **не** «LithTech Compiler» и не редактор: это утилита **сжатия/распаковки LTA**
(LZSS, окно 4096, look-ahead 17, собственный битовый поток). Своего кода мало (275 строк CLI +
325 парсер), вся суть в `libs/ltamgr` — 1 500 строк на биты, окно и скользящее дерево.

**Паритет достижим и уже наполовину доказан:** эталонная сборка под Linux собрана в этой
рекогносцировке (`build/ltc`, 19 объектных файлов, 2 правки под gcc + 2 шима), она
детерминирована, а формат я разобрал до уровня «чужой декодер, написанный только по чтению
исходников, восстанавливает 7/7 файлов байт в байт». Осталось портировать компрессор 1:1 —
и это единственная содержательная работа.

**Объём порта:** ~1 250 строк C++20 (биты 140 + окно/LZSS 460 + контейнер 220 + файловый слой 300
+ CLI 600) + тесты. Ни float-математики, ни выравниваний, ни зависимости от `size_t` — то есть
класс сложности M1/M3 из прошлого проекта, а не M4/M5.

## 2. Что именно сжато и чем

```

tools/LTC/commandlineparser.* 441   CCommandLineParser (тот же класс, что мы портировали в M1)
libs/ltamgr/lzsswindow.cpp    463   компрессор: скользящее окно + двоичное дерево поиска
libs/ltamgr/ltacompressedfile 318   контейнер .ltc: версия, токены, декодер
libs/ltamgr/ltabitfile.cpp/h  199   битовый поток (LSB-first внутри байта)
libs/ltamgr/ltafile.*         260   диспетчер: сжатый/несжатый поток по флагу
libs/ltamgr/ltafilebuffer.*   451   буферизованный FILE* (кэш 1024 байта)
libs/ltamgr/ltautil.cpp       235   IsFileCompressed (по расширению) и прочие утилиты
libs/ltamgr/ltahuffmantree.*  457   **мёртвый код** (см. §6.7)
```

`main.cpp` не парсит LTA вообще: он открывает входной `CLTAFile` (сжатый или нет — решается по
расширению), читает **по одному байту** и пишет в выходной `CLTAFile`. Вся «умная» работа — в потоке.

**Исправление (найдено на M1, проверено прогонами).** Сжатость выхода задаётся не расширением
`-out`, а строкой `CLTAFile OutFile(pszOutFile, false, bInFileCompressed ? false : true)` — то есть
это всегда **отрицание** сжатости входа. Отсюда:

* `ltc x.lta -out y.lta` кладёт **сжатые** данные в файл с расширением `.lta`;
* `ltc x.ltc -out y.ltc` кладёт **несжатые** данные в файл с расширением `.ltc`;
* режима «скопировать как есть» у инструмента нет вовсе — он всегда конвертирует.

Расширение влияет только на то, как читается **вход** (§6.3). Практическое следствие для корпуса:
входом годится любой файл, но имя обязано иметь расширение `.lta`/`.ltc`, если не задан `-out`.

## 3. CLI — измеренное поведение (не по чтению кода, а прогонами)

```
LTC <filename> [-out <file>] [-view] [-verbose] [-help]
```

| сценарий | stdout | код |
|---|---|---|
| `-help` | справка | 0 |
| без аргументов | справка + `A file to modify must be specified` | 1 |
| несуществующий файл | `Error: Unable to open the file X` | 1 |
| неизвестная опция `-bogus` | справка + `Unknown option: bogus` | 1 |
| `-view -out x` | справка + `-view and -out cannot be set. Please select only one.` | **1** |
| `-help` вместе с мусором (`-help -bogus`) | только справка (проверка `-help` идёт раньше сканирования опций) | 0 |
| `-` (один дезигнатор) | справка + `Unknown option: ` (имя опции — пустая строка) | 1 |
| `--out y x.lta` | справка + `Unknown option: -out` (дезигнатор съедает только первый `-`) | 1 |
| `x.lta -out` | справка + `A file name must be specified with -out` | 1 |
| `-out` без файла | справка + `A file to modify must be specified` (проверка файла идёт раньше проверки `-out`) | 1 |
| `noext` (без `-view`) | `Error: The input file does not have a proper extension.` + вторая строка | 1 |
| `noext -view` | **выводит содержимое, код 0** — `-view` обрабатывается до проверки расширения | 0 |
| `x.lta b c` (лишние слова) | лишние становятся глобальными параметрами, берётся первый | 0 |
| имя с пробелом `my file.lta` | `Error: Unable to open the file my` — слова склеиваются через пробел и снова делятся | 1 |
| нет расширения и нет `-out` | `Error: The input file does not have a proper extension.` + `Either specify an output filename or correct the extension.` | 1 |
| `x.LTA` без `-out` | молча создаёт `x.ltc` (**регистр расширения теряется**) | 0 |
| `x.lta` без `-out` | молча создаёт `x.ltc`; `x.ltc` → `x.lta` | 0 |
| .ltc с версией != 0 | `Error: Unable to open the file X` | 1 |
| успех | **ничего не печатает** | 0 |

Имя выхода без `-out`: ищется последняя точка, проверяется (без учёта регистра) `.LTA`/`.LTC`,
расширение заменяется на `.lta`/`.ltc` в нижнем регистре.

## 4. Формат `.ltc` — спецификация

Поток битовый; **биты внутри байта идут от младшего к старшему** (`CLTABitFile::SetBit`,
маска `0x01 → 0x80`), но многобитные поля пишутся **старшим битом вперёд** (цикл
`for(nCurrBit = 1; nCurrBit <= N; nCurrBit++) SetBit(val & (1 << (N - nCurrBit)))`).

```
32 бита   версия файла, MSB-first, сейчас всегда 0     -> 4 нулевых байта
далее     последовательность токенов:
  1 бит   1 = литерал:  8 бит значение (MSB-first)
  1 бит   0 = span:     12 бит offset, 4 бита (length - 2)
                        offset == 0  -> конец потока (EOS), length при этом пишется как 0
константы: NUM_OFFSET_BITS = 12, NUM_LENGTH_BITS = 4, WINDOW_SIZE = 4096,
           BREAK_EVEN_POINT = (1+12+4)/9 = 1, LOOK_AHEAD_SIZE = (1<<4) + 1 = 17
           => длина span 2..17 байт, литерал = 9 бит, span = 17 бит
```

Декодер: кольцевое окно 4096, `m_nDecWndPos` начинается с 1 (позиция 0 не пишется, поэтому
`offset == 0` однозначно означает EOS). Копирование span'а — побайтовое с продвижением обоих
указателей (то есть **перекрытие разрешено**, как в классическом LZSS).

**Проверка спецификации:** независимый декодер (Python, 60 строк, написан только по чтению
`ltacompressedfile.cpp`+`ltabitfile.h`, лежит здесь же как `decode.py`) восстановил все 7
тестовых файлов байт в байт, включая случайное 50 КБ, повторы на 18 КБ (переполнение окна) и
пустой файл.

## 5. Компрессор — что надо воспроизвести 1:1

`CLZSSWindow` — классическая схема LZSS Сторера–Шимански с **двоичным деревом поиска**:

* окно `m_Window[4096 + 17]` (последние 17 байт — «ghost edge» для прямых `memcmp`-подобных
  сравнений без проверки границ);
* дерево `m_Tree[4097]`, `ROOT_NODE = 4096`, `NULL_NODE = 0`, вставка через `AddNode()`
  (поиск самого длинного совпадения, при равенстве — более длинное выигрывает, ничьи решает
  порядок обхода), при точном совпадении всех 17 байт `ReplaceNode()` сразу заменяет узел;
* look-ahead наполняется до 17 байт, после чего `WriteToken()` выбирает: `len <= 1`
  (BREAK_EVEN_POINT) → литерал, иначе span; `m_nMatchLen` переносится в следующий вызов
  (совпадение, найденное при вставке предыдущей позиции, используется как кандидат);
* по закрытию файла `FlushLookAhead()` досбрасывает остаток и пишет EOS как `WriteSpan(0, 2)`.

Именно эти детали — порядок обхода дерева, «запасной» кандидат `m_nMatchPos/m_nMatchLen` и
поведение ghost-буфера на границе окна — определяют **байты** файла. Никакой эвристики «как
обычно делают LZSS» здесь применять нельзя: только построчный порт.

## 6. Квирки, UB и ловушки (пронумеровано — это основа для `porting-notes`)

1. **`-verbose` — мёртвый флаг.** `bool bVerbose` вычисляется в `main()` и нигде не читается;
   измерено: вывод 0 байт, файл идентичен прогону без флага. Порт обязан повторить это
   (принимать флаг и ничего не делать), а не «улучшать».
2. **Последний неполный байт битового потока теряется.** `CLTABitFile::Close()` не флашит
   `m_nCurrData`, поэтому хвост из 1..7 бит просто отбрасывается. Измерено: пустой файл → 6
   байт (32 бита версии + 17 бит EOS = 49 бит, 1 бит потерян), 1 байт → 7, 2 байта → 8. Это
   байтово-видимое поведение, его надо сохранить (и закрепить тестом).
3. **Сжатость определяется только по расширению.** `CLTAUtil::IsFileCompressed()` смотрит
   `.ltc` (без учёта регистра) и больше ничего; файл с чужим содержимым, названный `.ltc`,
   падает на проверке версии с `Error: Unable to open the file`. Обратный случай — `.lta`,
   внутри которого LTC-поток — будет прочитан как несжатый и скопирован как есть.
4. **Распаковка без `-out` перезаписывает одноимённый `.lta`.** `ltc x.ltc` пишет `x.lta`;
   если тот existed — он открывается на `wb` и уничтожается. Измерено: у файла меняется
   mtime при сохранении inode. Опасное, но это поведение оригинала → документируем.
5. **`strcpy` в `char pszOutFile[_MAX_PATH]` без проверки длины** (`main.cpp`, две штуки) —
   классический stack overflow на длинных путях. На Linux `_MAX_PATH == 256` из
   `ltbasedefs.h`. Решение по этому и подобным — как в прошлом проекте: сохранить семантику,
   но реализовать безопасно (`std::string`/обрезка) **с явной записью в porting-notes**, либо
   воспроизвести падение — решается на M1.
6. **`m_DecWnd` в `CLTACompressedFile::Open(READ)` не инициализируется** *(закрыто на M3:
   порт обнуляет окно, см. porting-notes Q6)* (обнуляется только
   `m_nDecWndPos = 1`). Span, ссылающийся на ещё не заполненную область окна, вернёт мусор
   со стека. На корректных файлах недостижимо (компрессор ссылается только назад, на уже
   записанное). Порт может либо обнулять окно (и это будет отклонением только для
   повреждённых файлов), либо сохранить как есть — предложение: обнулять и записать это в
   porting-notes как «единственное место, где порт определённее оригинала».
7. **`CLTAHuffmanTree` (457 строк) — мёртвый код.** Никто в дереве на него не ссылается
   (проверено `grep` по всему `libs/` и `tools/`); шапка `ltacompressedfile.h` обещает
   «adaptive huffman scheme», но реально используется LZSS. Порт его **не реализует**, в
   документации это фиксируется, чтобы не возникло вопросов «а где Huffman».
8. **Две правки под gcc уже известного класса** (MSVC утечка переменной цикла):
   `ltahuffmantree.cpp` (`nTestNode`) и `main.cpp` (`nCurrChar`). Обе — механические, смысл
   не меняют. Без них файлы просто не компилируются.
9. **`stricmp` нельзя определять макросом.** `ltbasedefs.h` под `__LINUX` сам объявляет
   `inline int stricmp()`, вызывающий `strcasecmp`; макрос `#define stricmp strcasecmp` в шиме
   переписывает имя самого объявления и даёт бесконечную рекурсию (пойман ASan: stack overflow
   в первом же вызове). Урок из прошлого проекта подтвердился на другом коде.
10. **MSVC-пути в инклюдах.** `ltamgr.h` подключает `"..\ltamgr\ltafile.h"` — gcc воспринимает
    обратные слэши как символы имени файла. Решается слоем `compat/` (скрипт `autocompat.py`
    в этой рекогносцировке сам создаёт симлинки и на backslash-имена, и на регистр:
    `ILTAAllocator.h` → `iltaallocator.h`).
11. **`ASSERT`/DEBUG-остатки.** В `CLZSSWindow::AddByte` живёт `static int32 nNumCalls` —
    счётчик, который никуда не выводится (на файл не влияет). `WriteSpan` содержит
    `ASSERT(nOffset < (1 << NUM_OFFSET_BITS))`, который в release-сборке MSVC мог быть отключён.
12. **`offset == 0` зарезервирован под EOS — коллизия невозможна (закрыто на M2).**
    `AddNode` начинается с `if(nWindowNode == NULL_NODE) return;`, а `NULL_NODE == 0`, поэтому
    позиция окна 0 никогда не попадает в дерево и не может стать `mMatchPos`. Значит, span с
    offset 0 в корректном потоке бывает только один — EOS. Проверено независимым разборщиком
    на всём корпусе (`golden/dump_tokens.py --assert`).

13. **Проверка версии на обрезанных файлах.** Заголовок читается циклом
    `nCurrVersion <<= 1; if (nVal) nCurrVersion |= (1 << nCurrBit)`. Из-за сдвига любой ненулевой
    бит уезжает в 31-й разряд, поэтому «версия валидна» ⟺ все 32 бита нулевые. Но `GetBit` при
    конце файла возвращает `false` и **не трогает** выходной параметр — вызывающий код читает
    неинициализированную переменную (UB). Наблюдаемое поведение эталона: файл из 0…8 нулевых
    байт считается валидным и декодируется в пустоту (код 0), любой ненулевой бит в первых 4
    байтах даёт `Error: Unable to open the file`. Порт фиксирует это как «бит при EOF = 0»
    (см. `docs/porting-notes.md`, Q10) и совпадает с эталоном на всех проверенных обрезках.

14. **`-view` идёт раньше проверки расширения, `-help` — раньше всего остального.** Порядок
    проверок в `main.cpp` — не косметика: он виден на кодах возврата (§3).

15. **Мусор в `.ltc` декодируется «успешно».** Файл `\0\0\0\0` + произвольные байты открывается
    (версия 0) и выдаёт несколько байт мусора с кодом 0 — спан'ы ссылаются на неинициализированное
    окно (§6.6). Воспроизведение этого случая — задача M3.

## 8. Измеренные факты (для гейтов и документации)

| вход | размер | `.ltc` | round-trip |
|---|---|---|---|
| пустой | 0 | 6 | OK |
| 1 байт | 1 | 7 | OK |
| 2 байта | 2 | 8 | OK |
| все 256 байт ×4 | 1 024 | 393 | OK |
| `abcabc…` ×2000 | 18 000 | 2 270 | OK |
| случайные | 50 000 | 55 905 (расширение!) | OK |
| текст LTA-подобный | 39 000 | 4 900 | OK |

* Детерминизм: два прогона → идентичные файлы (sha256 совпадает).
* Фазз: 200 файлов разной структуры и длины (включая границы окна) → 200/200 round-trip.
* Независимый декодер (Python, по спецификации) → 7/7 файлов идентичны оригиналу.
* Случайные данные **расширяются** (~+12 %): литерал стоит 9 бит. Это ожидаемо и должно быть
  закреплено тестом (паритет ≠ «сжимает», паритет = «те же байты»).

## 9. Корпус

* 9 настоящих `.lta` из прошлого проекта (`modelpacker/tests/data` в приватном репозитории;
  там же лежат ещё 117+72 `.ltb`) — они дают «реалистичный» вход 3–500 КБ.
* Синтетика (вход LTC всё равно байтовый): пустой, 1, 2, 255, 256, повторы, все 256 байт,
  случайные, тексты, файлы ровно 4095/4096/4097, 64 КБ, 1 МБ.
* Оракул — `ref/ltc` из эталонной сборки; корпус `golden/*.ltc` + `manifest.sha256`.
* Дополнительно: `.ltc`, произведённые **оригинальным** компрессором, проверяются портом на
  декодирование (`-view` и обратное сжатие → байт в байт исходник).

## 10. План милстоунов

| этап | содержание | гейт (критерий приёмки) |
|---|---|---|
| **M0** | эталонная сборка + корпус + детерминизм-свип | `ref/ltc` собирается, `golden/` из 40+ файлов, два прогона совпадают |
| **M1** | CLI 1:1: парсер, справка, коды возврата, генерация имён, `-view`/`-out`/`-verbose` | `cli_parity.sh`: stdout/stderr/код на 12 сценариях из §3 совпадают байт в байт |
| **M2** | битовый слой + `CLZSSWindow` 1:1 → **сжатие** | `ltc_parity.sh --against`: все `golden/*.ltc` воспроизводятся байт в байт |
| **M3** | декодер + `-view`, round-trip | `lta→ltc→lta` байт в байт на корпусе; `-view` = исходник; чужие `.ltc` из корпуса читаются |
| **M4** | тесты-инварианты, доки, второй компилятор | юнит-тесты (порядок бит, границы span 2..17, потеря хвоста, EOS, окно 4096), clang, «без предупреждений» для нового кода |

Порядок именно такой: сжатие первым, потому что оно определяет байты; декодер — почти
бесплатно после него, но он же и проверяет компрессор на корпусе.

## 11. Структура нового репозитория (`lithtech-ltc`)

```
ltc/
├── port/                 порт на C++20 (CMake, doctest)
│   ├── include/ltc/      bits, lzss, container, file, cli
│   ├── src/              то же в реализации
│   ├── tests/            unit + golden
```

## 12. Риски и открытые вопросы

1. **Байтовый паритет сжатия** — единственный настоящий риск: зависит от точного повторения
   дерева и ghost-буфера. Снимается построчным портом + гейтом на 40+ файлах; первые
   расхождения будут локализоваться дампером токенов (аналог `mp_dump_strips`: печатать
   последовательность токенов до первого расхождения — сделать сразу, это дешевле отладки).
2. **`-verbose`** — если у пользователя есть ожидание, что флаг что-то печатает: он не печатает
   (см. §6.1). Порт повторяет поведение.
3. **Перезапись `.lta` при распаковке** (§6.4) — опасное поведение оригинала. Порт может
   повторить (паритет) или отказаться и требовать `-out`; по умолчанию — повторить, с
   предупреждением в документации.
4. **Длинные пути** (§6.5) — решение по `strcpy` принять на M1 и записать в porting-notes.
5. **Нужен ли больший контекст**: если в будущем понадобится движковый читатель `.ltc`
   (`runtime/…`), он в объём не входит: делаем только `tools/LTC` + `libs/ltamgr` (сжатие).
