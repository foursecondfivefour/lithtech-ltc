# Паритет: что именно проверено

Короткий документ «одной страницей»: что порт обязан повторять, чем это проверено и
где он **сознательно** отличается. Подробности решений — `porting-notes.md`,
формат — `ANALYSIS-4.md`, этапы — `roadmap.md`.

Оракул везде — `ref-build/build/ltc`: LTC, собранный из оригинальных исходников
(`tools/LTC` + `libs/ltamgr`) под Linux. Отличия эталонной сборки от апстрима
перечислены в `ref-build/PATCHES.md` (две механические правки под gcc, четыре шима).

## Совпадает

| утверждение | как проверено | результат |
|---|---|---|
| сжатие: те же байты `.ltc` | 56 золотых файлов + фазз с детерминированными seed'ами | 56/56, 1500/1500 |
| сжатие на больших файлах | 4 файла по 1 МБ (монотонный 4 МБ, случайный, текст, период 17) | все совпадают |
| распаковка: те же байты `.lta` | 56 эталонных `.ltc` → файлы корпуса | 56/56 |
| `-view` | 56 эталонных `.ltc` → stdout | 56/56 |
| round-trip | сжал портом → распаковал портом | 56/56 |
| CLI: справка, сообщения, коды возврата, набор создаваемых файлов | дифференциальный гейт, 51 сценарий, stdout/stderr байт в байт | 51 OK, 0 FAIL, 0 SKIP |
| имена выходных файлов | отдельные сценарии + запись в каталог только для чтения | совпадает |
| поведение на мусоре с неверной версией | `.ltc` с версией ≠ 0 | `Error: Unable to open the file X`, код 1 |
| детерминизм | два прогона по корпусу, плюс `-verbose` | идентично |
| инварианты формата | независимый разборщик `golden/dump_tokens.py --assert` | 56/56 + 20 файлов выхода порта |

## Отличается (и почему это не исправляется)

**1. Поток `.ltc`, оборванный посреди токена.** В `CLTABitFile::GetBit` при конце
файла возвращается `false`, но выходной параметр не присваивается, а вызывающий код
в циклах чтения offset/длины/байта игнорирует возвращаемое значение. Эталон
достраивает токен из неинициализированного стека — результат зависит от содержимого
памяти и невоспроизводим. Порт считает недостающие биты нулями (Q10/Q10a).

Измерено `scripts/truncation_sweep.py`: для каждого префикса потока сравниваются
выходы обеих реализаций и отдельно классифицируется, попала ли обрезка ровно на
границу токена (там эталон упирается в конец файла при чтении флага и ведёт себя
детерминированно). На трёх файлах с шагом 1 байт — 176 расхождений, **все** внутри
зоны неопределённости, 0 вне неё. На корректных файлах (с настоящим EOS) расхождений
нет ни одного.

**2. Мусор после валидного заголовка, ссылающийся в незаписанную часть окна.**
Окно декодера в оригинале не инициализируется (Q6), порт обнуляет его. На корректных
потоках недостижимо (компрессор ссылается только назад). Видимый эффект только на
мусорном входе: эталон выдаёт 63 байта «со стека», порт — 46 (ровно разбор токенов).
В CLI-гейте такой сценарий (`junk_ltc`) сравнивает коды возврата и потоки, но не
содержимое.

**3. Имя выходного файла длиннее 255 символов.** Оригинал копирует его в
`char[_MAX_PATH]` через `strcpy` — переполнение стека (UB). Порт хранит имя в
`std::string` без ограничения длины (Q5). На реальных путях поведение идентично.

**4. `-verbose`.** В оригинале это мёртвый флаг: принимается и ничего не печатает.
Порт повторяет поведение, а не «исправляет» его (Q1).

## Как воспроизвести

```bash
ref-build/build.sh          # эталон из оригинальных исходников (нужен g++-14)
scripts/all_gates.sh        # вся приёмка: M0 → M4, ~3 минуты
```

Каждый гейт печатает PASS/FAIL и завершается с ненулевым кодом при любом расхождении.
